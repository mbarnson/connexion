  <name>Task 1: Create Draft 2020-12 validators and version-aware resolve_refs</name>
  <files>connexion/json_schema.py</files>
  <action>
In `connexion/json_schema.py`:

1. Add `Draft202012Validator` to imports from jsonschema:
   ```python
   from jsonschema import Draft4Validator, Draft202012Validator, RefResolver
   ```

2. Create `Draft202012RequestValidator` — assign directly as `Draft202012Validator` (no extensions needed, type arrays are native in 2020-12, no NullableTypeValidator needed):
   ```python
   Draft202012RequestValidator = Draft202012Validator
   ```

3. Create `Draft202012ResponseValidator` — extend Draft202012Validator with writeOnly checks (same pattern as Draft4ResponseValidator):
   ```python
   Draft202012ResponseValidator = extend(
       Draft202012Validator,
       {
           "writeOnly": validate_writeOnly,
           "x-writeOnly": validate_writeOnly,
       },
   )
   ```

4. Make `resolve_refs()` version-aware by adding a `spec_version` parameter:
   - Signature: `def resolve_refs(spec, store=None, base_uri="", spec_version=(3, 0, 0))`
   - In the inner `_do_resolve()` function, when `spec_version >= (3, 1, 0)`:
     - Still resolve the `$ref` target (retrieve the referenced object)
     - But preserve sibling keywords: save siblings before update, restore after
     - Specifically: capture all keys that are NOT `$ref` before the update, then after `node.update(retrieved)`, restore those siblings (they take precedence as per JSON Schema 2020-12 semantics where $ref is an applicator)
     - Still pop `$ref` from the node (connexion's internal pipeline expects resolved schemas)
   - For `spec_version < (3, 1, 0)`: behavior unchanged (existing code path)
   - Default parameter `(3, 0, 0)` ensures zero regression for all existing callers

Place the new validators after the existing Draft4 validators (after line 154) to keep the file organized.
  </action>

**In `connexion/spec.py`:**

   - Check if the error relates to `nullable` by inspecting `e.message` for "nullable" or checking if `e.schema_path` mentions additional properties and `e.instance` contains nullable
   - When detected, append actionable migration guidance to the error message:
     ```
     "\n\nHint: OpenAPI 3.1 removed the 'nullable' keyword. "
     "Use type arrays instead:\n"
     "  Before:  type: string\n"
     "           nullable: true\n"
     "  After:   type: [string, 'null']"
     ```
   - Per user decision: this is STRICT REJECTION at load time, not auto-conversion

2. In `OpenAPI31Specification.__init__()`, override to pass `spec_version` to `resolve_refs()`:
   - Override `__init__` to call parent logic but use `resolve_refs(raw_spec, base_uri=base_uri, spec_version=(3, 1, 0))` instead of the base class's `resolve_refs(raw_spec, base_uri=base_uri)`
   - The cleanest approach: override `__init__` to replicate the parent init but pass spec_version to resolve_refs. Or add a class-level `_spec_version` attribute and modify the base `Specification.__init__` to pass `getattr(cls, '_spec_version', (3, 0, 0))` to resolve_refs. Choose whichever approach is cleaner — the goal is that OpenAPI31Specification passes `spec_version=(3, 1, 0)` to resolve_refs.

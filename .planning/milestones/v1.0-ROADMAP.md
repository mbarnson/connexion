# Milestone v1.0: OpenAPI 3.1 Support

**Status:** SHIPPED 2026-02-06
**Phases:** 1-4
**Total Plans:** 11

## Overview

This roadmap delivered comprehensive OpenAPI 3.1.0 support to Connexion through four focused phases: establishing version detection and routing infrastructure, upgrading the validation engine to JSON Schema 2020-12, implementing OAS 3.1 structural features, and proving correctness through comprehensive testing. The journey took Connexion from "3.1 specs fail to load" to "SongViber's 3.1 spec loads, validates, and generates working code."

## Phases

### Phase 1: Spec Detection & Schema

**Goal**: Connexion correctly detects OpenAPI 3.1.x specs and routes them to dedicated handling with proper meta-schema validation

**Depends on**: Nothing (first phase)

**Requirements**: SPEC-01, SPEC-02, SPEC-04, SPEC-05

**Plans**: 2 plans

Plans:

- [x] 01-01-PLAN.md -- Bundle OAS 3.1 meta-schema, create OpenAPI31Specification class, update version routing
- [x] 01-02-PLAN.md -- Test suite proving version detection, routing, validation, and zero regression

**Details:**
- Bundled official OpenAPI 3.1 meta-schema (Draft 2020-12 based)
- Created OpenAPI31Specification as sibling class to OpenAPISpecification
- Three-way version routing: < (3,0,0) -> Swagger2, >= (3,0,0) and < (3,1,0) -> OpenAPI3.0, >= (3,1,0) -> OpenAPI3.1
- Unsupported versions (4.0+) raise InvalidSpecification with helpful message
- 22 tests covering all Phase 1 requirements

### Phase 2: JSON Schema 2020-12 Validation

**Goal**: All request and response validation for 3.1 specs uses JSON Schema 2020-12 semantics with full support for type arrays, strict nullable rejection, and updated keywords

**Depends on**: Phase 1

**Requirements**: VALID-01 through VALID-10

**Plans**: 3 plans

Plans:

- [x] 02-01-PLAN.md -- Draft 2020-12 validators, version-aware $ref resolution, nullable rejection, spec_version on operations
- [x] 02-02-PLAN.md -- Wire spec_version through middleware to all validators, comprehensive VALID-* test suite
- [x] 02-03-PLAN.md -- Migrate SongViber spec from nullable: true to type arrays

**Details:**
- Draft202012RequestValidator and Draft202012ResponseValidator created
- Version-aware resolve_refs preserves $ref siblings for 3.1, legacy behavior for 3.0
- Strict nullable rejection with actionable error messages
- spec_version flows from Specification -> Operation -> Middleware -> Validators
- SongViber spec migrated: 14 nullable fields converted to type arrays
- 28 tests covering all VALID-* requirements

### Phase 3: OAS 3.1 Features

**Goal**: All OpenAPI 3.1 structural features are recognized, parsed, and accessible

**Depends on**: Phase 2

**Requirements**: SPEC-03, FEAT-01 through FEAT-06

**Plans**: 3 plans

Plans:

- [x] 03-01-PLAN.md -- Spec-level features: webhooks property, pathItems defaults, minimal document support, jsonSchemaDialect property
- [x] 03-02-PLAN.md -- Operation-level features: OpenAPI31Operation class, mutualTLS recognition in SecurityHandlerFactory
- [x] 03-03-PLAN.md -- Comprehensive test suite for all Phase 3 features

**Details:**
- webhooks property returns empty dict when not present (safe for iteration)
- json_schema_dialect property returns None when not present
- paths defaults to empty dict for minimal document support
- OpenAPI31Operation carries json_schema_dialect from spec
- mutualTLS returns security_passthrough (cert validation delegated to infrastructure)
- 25 tests covering all FEAT-* and SPEC-03 requirements

## Milestone Summary

**Key Decisions:**

- OpenAPI31Specification as sibling class (not subclass) to OpenAPISpecification
- Strict nullable rejection (not backwards-compat) — SongViber spec updated
- Version-aware resolve_refs with spec_version parameter for $ref sibling preservation
- mutualTLS via security_passthrough to avoid middleware ordering conflicts
- Inline test fixtures for self-contained, fast tests
- Kitchen-sink integration pattern for comprehensive feature testing

**Issues Resolved:**

- OAS 3.1 meta-schema doesn't prohibit nullable (solved with explicit detection before meta-schema validation)
- $ref in Operation Objects doesn't allow siblings in OAS 3.1 (tests moved to schema level)
- Form-encoded data parsed as arrays by connexion (schemas use type: array with items)

**Issues Deferred:**

- None. All requirements fully implemented.

**Technical Debt Incurred:**

- None. Clean implementation with zero TODO/FIXME/HACK in new code.
